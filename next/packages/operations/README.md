# Native operations

Implemented modules: native service definitions/registration scripts, installer preflight, pinned private-runtime check, independently trusted Ed25519 release manifests and file hashes, staging activation with health callback and rollback, SQLite snapshots encrypted with age, and staged recovery with audit-preserving automation pause.

The operating commands run through `apps/cli/main.ts` (or its built JS counterpart):

```sh
node apps/cli/main.ts setup --data-dir /path/to/data
node apps/cli/main.ts backup --data-dir /path/to/data --age /absolute/path/to/age --recipient age1PUBLIC_RECIPIENT --output /path/to/backups
node apps/cli/main.ts restore --data-dir /path/to/data --age /absolute/path/to/age --identity /separate/identity.txt --archive /path/to/backup.tar.age
node apps/cli/main.ts verify-release --release /path/to/signed-release --trusted-key /administrator/trusted-release-public.pem
node apps/cli/main.ts service-bundle --platform linux --role control --output /path/to/service-bundle
```

CLI backup/restore is offline maintenance and refuses any live shared instance-lock owner; stale instance locks are recovered only under the exclusive acquisition gate described below. Programmatic online backup requires a `quiesce` callback freezing writes and blob garbage collection through snapshot completion. The application can supply `Repository.backup` as snapshot callback. No open SQLite-file copy is used.

Restore decrypts into a protected staging directory, enforces stream/file/count limits, rejects symlinks/hardlinks/traversal/duplicate case-insensitive paths, validates exact manifest contents and hashes, schema and SQLite integrity before target mutation. It then prepares a fresh recovery generation using normal repository transactions, revokes sessions and worker credentials, expires leases and pauses schedules. Running/dispatched actions become `effect_unknown`. The previous target directory remains available for rollback. Existing UNIX target ownership is preserved; fresh UNIX installs can pass explicit service uid/gid. Windows restore ACL inheritance must be validated on the target installation. No claim of physical SSD erasure is made.

The firmenweite `recovery-state` document is stored in the first/default area with company ID as document ID. The current schema's company/kind/id primary key prevents writing that same ID in several areas. Every affected session/action/worker/schedule is updated in its own exact scope. The runtime must consult the central recovery state before model/tool dispatch, channel outbox and scheduled work; a successful restore is not permission to repeat external effects.

`activateRelease` verifies signature and hashes before copying only manifest-listed files. Its `beforeActivate` callback must stop new work, verify a backup and stop services. Its `healthCheck` callback must launch/check the new service and stop a failed process; `restartPrevious` must restart the previous service when activation fails. Automatic release download/install remains disabled without a separately configured trust key. Cross-schema migration is deliberately refused until a tested migration/restore plan exists.

The generated native registration scripts are executable installation artifacts; generating one does not claim that a service was installed. Run the script from its bundle directory after installing the verified release/private runtime. Linux uses systemd and a dedicated account, macOS a LaunchDaemon and hidden dedicated account, Windows a WinSW service running as LocalService with explicit data/program ACLs. Each script checks for the built entrypoint and private runtime. Windows additionally requires the pinned wrapper inside the signed release.

## Validation and remaining release gates

Local automated tests cover real age encryption/decryption, wrong keys, modified ciphertext, malicious linked archives, manifest mismatch, size limits, fresh restore, retained prior state, generation/credential/schedule changes and audit-chain verification. Installer tests cover correctly/wrongly signed manifests, modified binaries, symlink replacement, incompatible schema, failed-health rollback, whitelist staging, renderer escaping, shell syntax and macOS `plutil` validation.

For real age tests set `IRONCREW_TEST_AGE` and `IRONCREW_TEST_AGE_KEYGEN` to verified local binaries. Tests explicitly skip when those tools are unavailable; this is not a passed recovery gate on that host. This macOS run executed the tests using actual age 1.3.2.

Still required before release: full native install/reboot/update on each stated OS/architecture, a real signed release including packaged production dependencies and private runtime, Windows ACL/service validation, remote backup targets, confirmed retention and scheduling setup, update maintenance-window consent, and external-effect reconciliation/re-enable UI tied to the CEO. Renderer tests are not OS installation evidence. Automatic updates and periodic backups must not be enabled merely because these functions exist.

## Shared instance ownership and interrupted-lock recovery

Control, CLI setup, offline backup and offline restore all use `acquireInstanceLock`. The data directory's `instance.lock` contains a version, PID, random ownership token, purpose and creation time. Every acquisition and release first obtains `.instance-acquire.lock` with exclusive file creation. A dead legacy PID-only instance lock can be replaced only while holding that gate. A live owner, unreadable/malformed marker or abandoned acquisition gate blocks startup. Release verifies both the inode/device and ownership token before removing a file; it never removes a replacement belonging to another process.

Restore preserves ownership across directory replacement. Before activation it holds the acquisition gate, creates a stable `.<data-directory-name>.ironcrew-directory.lock` marker beside the data directory, and places the same ownership record into validated staging. The sibling marker fences new startup even between the two directory renames. Fresh data-directory creation uses this same sibling gate; normal startup of an existing directory needs no write permission on its parent. Restore already requires parent-directory write permission for the directory swap. After activation the helper removes only its verified markers from the retained prior directory, transfers ownership to the new inode, then releases the sibling marker. CLI holds the instance lease for the entire backup/restore operation, including validation and encryption.

If a process crashes while holding an acquisition or directory-transition marker, recovery is deliberately manual. The error includes the exact marker path. Stop the control service and all offline CLI operations; inspect that marker's PID/purpose/token and verify the recorded process no longer exists (`kill -0 PID` on POSIX, `Get-Process -Id PID` on Windows). For a directory-transition marker, also inspect the data directory, validated restore output and retained `.before-recovery-*` directory to select the consistent data tree before clearing the marker. Remove only the identified abandoned marker after this check, then restart. Never delete a marker while its PID is still active; PID reuse is treated conservatively as a live owner.

`tests/integration/instance-lock.test.ts` starts actual competing control processes, verifies ownership-change rejection and abandoned-gate fencing, pauses a real offline CLI backup while checking central startup refusal, and completes actual age-encrypted CLI backup/restore. It also attempts startup during the deliberate restore rename gap and verifies that no replacement empty data directory appears.

## Scheduled encrypted backups and maintenance plans

The control integration is `MaintenanceService({repo, directory, onlineBackup, now?, currentVersion?, releaseLifecycle?})` with routes registered by `registerMaintenanceRoutes`. `onlineBackup({ageExecutable, recipient, outputDirectory})` must return the real `BackupResult` after draining writes, scheduler work and artifact GC. The application supplies that quiesced callback. The maintenance tick runs after the normal background tick has completed, avoiding a callback waiting for its own background pause. No backup policy is enabled by creation.

Create a company-scoped CEO policy through `POST /api/v1/maintenance/backup-policies` with `name`, five-field `cron`, IANA `timezone`, public age `recipient`, absolute pinned `ageExecutable` and absolute `destination` outside the company data tree. Retention defaults are a **disabled proposal** for seven distinct daily versions and four weekly versions. Set `retention.enabled` explicitly in the proposed policy if cleanup is intended. Policy changes are new proposals, each needing its own proof and activation; pause the superseded policy explicitly.

`POST /api/v1/maintenance/backup-policies/:id/probe` accepts a transient administrative `identityPath`. It creates an actual encrypted backup, restores it to isolated temporary storage, verifies the company identity and SQLite audit, and records the archive hash and successful recovery result. The identity path and private key are never persisted. `.../:id/activate` requires this exact policy's matching, untampered proof archive, at most 30 days old. `.../:id/pause` disables future jobs. Execution is a durable CAS claim with one catchup after downtime; the local-time slot suppresses repeated DST slots. Interrupted jobs stay `effect_unknown`, without blind repetition. Existing recovery dispatch fences suppress the maintenance tick.

Retention considers only archive records produced by this policy/fingerprint. It pins the proof archive, then keeps the newest archive for each selected local day/week. Before deletion it verifies canonical containment, regular-file identity and SHA-256, moves into a private quarantine and verifies the same bytes again. Foreign files are never enumerated as deletion candidates; altered registered files remain present and create a retention issue. If a concurrent replacement prevents safe restoration of a quarantined file's original name, its bytes remain in the private quarantine for operator inspection.

Update policies (`POST /api/v1/maintenance/update-policies`) bind a separately configured Ed25519 public trust key, installation directory, active verified backup policy, allowed semantic-version classes and a cron/IANA maintenance window. Only patch updates are proposed by default; there is no automatic release deployment. `POST /api/v1/maintenance/updates` verifies a local signed release and creates a plan bound to the full manifest hash, current version and policy fingerprint. `.../updates/:id/approve` is an explicit CEO decision, valid for 24 hours; `.../update-policies/:id/revoke` prevents future application. `.../updates/:id/apply` checks the class, current base version, trust, hashes and window again, takes a fresh encrypted backup, stages/verifies the release, then invokes the configured service lifecycle and real healthcheck. The window and revocation are checked again just before activation. Concurrent plans share one durable installation guard.

Production application uses the independently configured external updater (`IRONCREW_UPDATER_CONFIG`); a separately injected `releaseLifecycle` remains a local integration-test interface. The external service stops the control process, creates a fresh offline backup under the data owner's identity, activates the signed release and checks exact manifest/version plus a new instance ID. Its database and queue helpers also run under the data owner's identity. Root retains only administrative service and release operations. Without either configured executor the apply route reports `maintenance_executor_not_configured`. Unknown effects retain the installation guard; confirmed success or verified health rollback can clear only this job's pause. See the packaged updater guide for administrative ownership, bootstrap installation and manual reconciliation.

Optional `autoApplyApproved` queues an already explicitly approved plan in its maintenance window. Approval expires after 24 hours and is never extended or created automatically by the scheduler. Native Linux systemd and local macOS process tests are separate evidence; the remaining platform and production-account acceptance is still outstanding.

Validation: `tests/integration/maintenance.test.ts` performs real age encryption/decryption, isolated SQLite restore probes, durable concurrent schedule claims, safe retention and signed release directory activation/rollback. `tests/unit/maintenance.test.ts` verifies IANA/DST windows, retention selection and update classification. The application-level quiesce route is independently covered by the online-backup API test.
