# Native Google-Dateien

Die neuen Fähigkeiten gehören zum bestehenden `gdrive`-Connector. OAuth, Bereichsbindung, Mandate, Aktionsbelege und konkrete CEO-Freigaben verwenden denselben Broker wie die übrigen Integrationen. Jeder native Aufruf trägt `targetConfigSha256`; Änderungen an der vollständigen Zielkonfiguration entwerten diese Bindung. Vor jedem tatsächlichen HTTP-Aufruf wird die aktuelle Aktionsautorisierung erneut geprüft.

| Werkzeug                 | Konkrete Wirkung                                                                                           | Konfliktgrenze                                                                   |
| ------------------------ | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `gdocs.create`           | Neues natives Google-Dokument aus Klartext im explizit erlaubten Drive-Ordner                              | Neue Datei; Aktion/Quellhash in Drive-AppProperties zur Nachprüfung              |
| `gdocs.read`             | Dokument, Tabs und Revisions-ID lesen                                                                      | Nur freigegebene Dokument-ID                                                     |
| `gdocs.append`           | Text am Ende eines expliziten Tabs ergänzen                                                                | `writeControl.requiredRevisionId`                                                |
| `gdocs.replace`          | Einen expliziten UTF-16-Indexbereich eines Tabs ersetzen                                                   | Atomare Löschung/Einfügung unter `requiredRevisionId`                            |
| `gsheets.read`           | Begrenztes Zellrechteck lesen, materialisierte Werte und Inhaltshash zurückgeben                           | Nur freigegebene Spreadsheet-ID                                                  |
| `gsheets.create`         | Neues natives Spreadsheet mit einem Blatt und typisierten Literalwerten                                    | Neue Datei im autorisierten Kontowurzelbereich                                   |
| `gsheets.version.create` | Freigegebenen Rechteckhash prüfen, konkrete relative Zelländerungen auf eine neue Tabellenfassung anwenden | Quelle bleibt unverändert; keine vorgetäuschte atomare Sheets-Revisionsbedingung |
| `gslides.create`         | Neue leere native Präsentation                                                                             | Neue Datei im autorisierten Kontowurzelbereich                                   |
| `gslides.read`           | Präsentation, Revisions-ID und Folienobjekte lesen                                                         | Nur freigegebene Präsentations-ID                                                |
| `gslides.text.replace`   | Text eines expliziten vorhandenen Folienobjekts ersetzen                                                   | `writeControl.requiredRevisionId`                                                |

Alle Schreibfähigkeiten verlangen eine konkrete Freigabe. Es gibt keinen frei übergebenen Google-`batchUpdate`-Body und keine beliebigen Feldmasken, Freigaben, Skripte oder Formeln. `resourceIds` enthält die erlaubten Dokument-/Tabellen-/Präsentations- bzw. Ordner-IDs. Für Sheets-Neuerstellung muss zusätzlich `create:spreadsheets`, für Slides-Neuerstellung `create:presentations` administrativ freigegeben sein. Neu erzeugte IDs werden nicht automatisch für spätere Änderungen in die Allowlist aufgenommen.

Google Docs und Slides prüfen die geforderte Revision serverseitig. Eine veraltete Docs-Revisionsbedingung liefert laut API HTTP400; der Adapter behandelt abgelehnte Revisions-/Änderungsbedingungen als Konflikt. Es wird kein schwächeres `targetRevisionId` verwendet. Die [Docs-Schreibkontrolle](https://developers.google.com/workspace/docs/api/reference/rest/v1/documents/batchUpdate#WriteControl) und [Slides-Schreibkontrolle](https://developers.google.com/workspace/slides/api/reference/rest/v1/presentations/batchUpdate#WriteControl) liefern den zugrunde liegenden Vertrag.

Die [Sheets-Batch-API](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate) hat keine entsprechende `writeControl`-Bedingung. Deshalb bedeutet `gsheets.version.create` ausdrücklich: neuer Ausschnitt als Werte-Snapshot, keine vollständige Arbeitsmappenkopie und kein Überschreiben des alten Dokuments. Formeln der Quelle werden beim Lesen materialisiert; neu eingegebene Zeichenketten bleiben `stringValue`, auch wenn sie mit `=` beginnen. Das schützt vor unbeabsichtigter Formelausführung. Unterstützt werden höchstens 500 Zeilen, 50 Spalten und insgesamt 1 MiB Zellwerte; ein Versionsauftrag ändert höchstens 100 konkrete Zellen. Für Zellwerte und native Erstellung gelten die offiziellen [Values-Read](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/get)- und [Spreadsheet-Create](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/create)-Verträge.

Neue Docs entstehen in einem einzelnen Drive-Multipart-Aufruf mit nativem Ziel-MIME-Typ und Klartextquelle; das ist eine ausdrücklich unterstützte [Google-Konvertierung](https://developers.google.com/workspace/drive/api/guides/manage-uploads#upload_and_convert_media). Originales Markdown aus einem Recherchebericht wird dabei als Klartext übertragen; es wird keine typografische Markdown-Konvertierung behauptet. Neue Slides sind zunächst leer gemäß [Presentations.create](https://developers.google.com/workspace/slides/api/reference/rest/v1/presentations/create); vorhandene Objekte können später gezielt bearbeitet werden. Ein vollständiger Präsentationsdesigner gehört nicht zu diesen Werkzeugen.

Recherchelieferungen unterstützen `nativeFormat: "google-doc"` zusammen mit `folderId`, `targetId` und `targetConfigSha256`. `ResearchService.deliver` liest den vorhandenen Bericht aus der lokalen Blobablage, prüft dessen SHA256 und bindet diese tatsächlichen Inhalte an die Freigabe. Nach erfolgreicher nativer Erstellung werden externe ID und Version gespeichert. Ein bereits ausgelieferter Bericht wird beim Wiederholen nicht erneut erstellt. Ein unklarer Schreibausgang muss abgeglichen werden; es gibt keinen automatischen Schreibretry.

Die vier Vertragstests in `tests/contracts/integrations-google-workspace.test.ts` bedienen reale lokale HTTP-Endpunkte nach diesen offiziellen Protokollen. Sie prüfen alle zehn Fähigkeiten, genaue Request-Bodies, Revisionskonflikte, typisierte Werte, Quelländerungen, fremde Ressourcen, Konfigurationsänderungen und ausbleibende Schreibwiederholungen. `tests/integration/research-google-workspace.test.ts` prüft zusätzlich den tatsächlichen SQLite-Auftrag/Artefakt/Freigabeweg bis zur HTTP-Auslieferung des gespeicherten Rechercheberichts. OAuth wird separat mit einem echten lokalen TLS-Tokenserver getestet. Es wurden keine echten Google-Konten genutzt; Providerberechtigungen, konkrete Kontoscopes und Livewirkungen müssen am vorgesehenen Konto gesondert abgenommen werden.
