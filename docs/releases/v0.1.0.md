# IronCrew 0.1.0 — 2026-09-05

IronCrew beginnt mit diesem Release seine eigene Produktversionsreihe.
Die vorherige `2.8.0` folgte der übernommenen Versionsnummerierung; sie bleibt
unverändert als historische Veröffentlichung bestehen. `0.1.0` setzt ihren
Quellstand fort und setzt keine Firmendaten zurück.

## Änderungen

- Produkt- und API-Version auf `0.1.0` vereinheitlicht.
- Eng begrenzter Versionswechsel von `2.8.0` auf `0.1.x` für native und
  Docker-Installationen; normale Downgrades bleiben gesperrt.
- Der aktuelle Main-Release wird ausdrücklich als „Latest“ veröffentlicht.
  Das historische `2.8.0` wird vom neuen Code nicht erneut als Update angeboten.
- Deutsche README mit aktuellem Office, Abteilungsfokus, Mitarbeiterübersicht,
  mobiler Ansicht und Versionsverwaltung.
- Neuer Docs-Index, Schnellstart, Bedienungsleitfaden und reproduzierbare
  Screenshot-Aufnahmen mit dokumentierter Testdatenherkunft.
- Portkorrektur für macOS und lokal gebundene Entwicklungsstarts in den Anleitungen.

Das enthaltene Company OS bietet den gemeinsamen CEO-/Task-/Run-Workflow,
das moderne Firmengebäude, 20 Originalfiguren, Junior-/Senior-/Lead-Level,
Lead-Delegation und Sternebewertungen, Modellrouting, Freigaben, Budgets,
Memory und native Runner. Konkrete Grenzen einzelner Integrationen stehen in
[Master-Prompt-Abdeckung](../MASTER_PROMPT_COVERAGE.md).

## Installation und einmaliger Versionswechsel

**Bestehende 2.8.0:** Verwende zwingend den Updater aus einem separaten
`v0.1.0`-Checkout. Der bisherige Updater kennt die Ausnahme noch nicht.
[Exakte native und Docker-Befehle](../RELEASES.md#wechsel-von-280-auf-010).

**Neue Installation:** [Erste Schritte](../GETTING_STARTED.md), für einen
Dauerbetrieb [Releases und Updates](../RELEASES.md).

Datenbank, Anhänge, private Figuren, Vault und Konfiguration gemeinsam sichern.
Es gibt keine automatische Datenbank-Abwärtsmigration. Normale Service- und
Runnerprüfungen sowie Commit-/Image-Digest-Prüfungen bleiben erhalten.
Das Release-Image unterstützt zunächst Linux/amd64.

## Prüfung und Grenzen

Die Veröffentlichung setzt erfolgreiche CI- und Plattformprüfungen desselben
Main-Commits voraus. Regressionstests prüfen den Versionswechsel, abgewiesene
Downgrades, veraltete Updateziele und die Latest-Auswahl bei verspäteten Releases.
Der separate Browserlauf erzeugt Screenshots aus einer neuen Testfirma und
prüft die dokumentierten Ansichten.

Die Bildschirmaufnahmen enthalten keine echten Provider-Runs und keine
produktiven Firmendaten. Authentifizierte CLI-Runs und die Wiederherstellung auf
dem eigenen System bleiben Betreiber-Abnahmeschritte. Der Release bedeutet keine
Installation oder Aktualisierung auf einem Kundensystem.
